# 小圈圈客服接入共创知识库 — 实施计划（2026-10）

## Context（为什么做）

右下角常驻的客服「小圈圈」（`web/src/components/CircleWidget.tsx`）目前只吃一张自己维护的问答表 `cs_faq`——线上仅 **6 条**，全是「怎么入驻 / 隐私 / 安全」这类新手问题。

而站内的共创知识库 `/entries` 已经有 **49 条已核验（sourced / corroborated）的实操知识**：Excel 透视表、VLOOKUP、什么是 MCP、公文格式、Suno 用法……很多本来就是新手会张嘴问的。这些知识现在只对 Agent 飞轮开放，**对访客这一侧是浪费的**。

本次改动：让小圈圈在**自己的问答库答不上时**，转去共创知识库找答案，用**简短要点 + 原文链接**回给用户，并注明「社区共创」。

用户已确认的三个选择：
1. **检索方式**：问答库优先，答不上再查共创库兜底（不合检索）。
2. **来源标注**：明确注明「社区共创」并附 `/entries/:id` 原文链接。
3. **回答形态**：保持小圈圈简短口语（≤120 字），2-3 句要点 + 链接看完整步骤。

## 方案总览

沿用 `ask()` 现有单入口，在**内部加一条兜底分支**，路由与前端均不改主流程：

```
用户提问
  └─ 照旧：IDF 检索 cs_faq
       ├─ 命中足够强（ranked[0].s >= THR）→ 现状逻辑（mode:'llm' / 'kb' 等），一字不改
       └─ 答不上（无命中 或 最高分 < THR）
            └─ 新增：lookupEntries({ q, scope:'answer', limit:3 }) 查共创库
                 ├─ 有可引用条目 → 注入 LLM 上下文，mode:'entry'，带「社区共创」出处 + 原文链接
                 └─ 仍无 → 维持现状 mode:'none'（引导去「新手上手」/ 反馈），行为不变
```

## 具体改动

### 1. 后端核心：`server/services/customerService.js`

- **可测性**：把直接调用的 `chat` 改为模块级可变引用，新增 `export function _setLlmForTest(fn)`（与 `companionChatService.js` / `companionWritingService.js` 同款模式），调用处改用该引用。
- **命中判定复用**：沿用文件内已有的阈值 `THR = 1.5` 与 `scoreAll()` 结果 `ranked`。新增一个内部判定：`const answered = ranked.length > 0 && ranked[0].s >= THR;`
- **兜底分支**（放在 cs_faq 路径判定「答不上」之后、返回 `mode:'none'` 之前）：
  - 调 `lookupEntries({ q, scope: 'answer', limit: 3 })`（`server/services/entryService.js`，**复用现成检索**，不新写查询）。
  - `scope:'answer'` 是硬要求：只放行 `sourced` / `corroborated`，**绝不让 `stub` / `proposed` / `contested` 进客服回答**（与小圈圈「绝不编造」原则一致）。
  - 有命中时组装共创上下文（每条取 `title` + `excerpt`，附 `state` / 署名 `curatorName` / `id`），在现有 system prompt 基础上**补一条规则**：这些条目来自「社区共创」，须注明是社区共创内容并给出条目链接，不替第三方厂商背书；保持简体中文、口语、≤120 字。
  - 返回：`mode: 'entry'`，`srcNote: '来自社区共创知识 · 《标题》'`，`link: { label: '看这条共创知识', href: '/entries/' + id }`，`quick` 照旧。
  - LLM 不可用（`chat` 返回 null）时：降级为直接给该条目的 `excerpt` 摘要 + 链接，不空手。

### 2. 测试基建：`server/tests/app.js`

- 补挂客服路由 `app.use('/api/cs', customerServiceRouter)`（该文件目前**漏挂** `/api/cs`，是一处「测试 app 与 index.js 漂移」，顺手补齐，且本次需要它做路由级契约测试）。

### 3. 新增契约测试：`server/tests/cs-entry.test.js`

用内存 SQLite + `supertest`，参考 `server/tests/entry.test.js` 的造数模式（`createEntry` + `db.ensureEntriesTables()`）。断言场景：

- **问答库优先**：cs_faq 命中时，LLM 收到的上下文只含 faq，**不含** entries（可 mock 记录调用参数断言）。
- **兜底生效**：cs_faq 答不上 + 共创库有可引用条目 → `mode:'entry'`、`srcNote` 含「社区共创」、`link.href` 指向 `/entries/:id`、LLM 上下文含该条目。
- **只取可引用态**：造一条 `proposed` 的条目，确认**不被打给客服**（`scope:'answer'` 生效）。
- **边界**：两边都答不上 → `mode:'none'`（维持原引导，行为不回退）。
- **降级**：LLM 返回 null 时，共创分支仍能给摘要 + 链接，不抛错。

## 关键纪律（红线）

- 只用 `scope:'answer'`，共创库中未核验的草稿一律不进客服回答。
- 共创内容必须标「社区共创」+ 原文链接，不当平台自有结论讲（呼应平台「不替他人内容背书」）。
- 回答压成要点，不逐字搬运整段正文。
- **免发版**：纯服务端改动，不涉及 MCP 工具 / 技能包，无需 bump 四大版本点。

## 验证方式

1. **单测**：项目根 `npm test`（`node --test --test-concurrency=1 "server/tests/**/*.test.js"`），重点看新增 `cs-entry.test.js` 全绿。
2. **本地接口**：起服务后 `curl -X POST localhost:3001/api/cs/ask -H 'Content-Type: application/json' -d '{"question":"VLOOKUP 怎么用"}'`，确认返回 `mode:'entry'` + 社区共创出处 + `/entries/:id` 链接；再问「怎么入驻」确认仍走原 faq 路径。
3. **前端实测**：本地起 web，点右下角小圈圈，分别问一个新手问题（入驻类）和一个实操问题（VLOOKUP / MCP），确认气泡、出处小字、链接跳转正常（前端预计**零改动**——`CircleWidget.tsx` 已支持 `text/srcNote/link` 渲染；若文案偏差再微调）。
4. **线上核验**：部署后对 `https://aibbs.chat/api/cs/ask` 同法抽查一次。

## 不改动的部分（避免过度设计）

- 不改 `CircleWidget.tsx` 主逻辑、不改 `/api/cs` 路由契约、不动 `cs_faq` 表结构、不给 `lookupEntries` 加新查询。
- 不做「两库合并统一打分」——本次按用户选择只做兜底。
